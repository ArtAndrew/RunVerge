# Result decisions and bounded teams — contract 0.4

Server/web: Elastic-2.0. This document describes implemented boundaries; it does not replace the full work orders or certify a complete product. Public DTOs come from `internal/domain`; OpenAPI and JSON Schema are generated by `cmd/contracts`. Client SDKs implement these public boundaries independently under Apache-2.0.

## Exact result decision

`GET /tasks/{id}/candidates` and `/decisions` return tenant-scoped cursor pages (default 50, maximum 100). `GET /tasks/{id}/children` lists direct children with the same pagination. A candidate binds one task, current run, operation and immutable artifact version to the SHA-256 of its exact UTF-8 content. It is evidence of which output was saved, not evidence that the content is true.

`POST /tasks/{id}/review` returns a Task, accepts an Idempotency-Key and requires:

```json
{
  "expected_version": 7,
  "candidate_id": "opaque-candidate-id",
  "artifact_id": "opaque-artifact-id",
  "artifact_version": 1,
  "content_digest": "64-lowercase-hex-characters",
  "decision": "accept",
  "reason": "optional for accept"
}
```

Allowed decisions are `accept`, `reject`, `request_changes`; the latter two require a nonblank reason. Reasons are at most 4096 UTF-8 bytes. The server re-reads the saved content and checks all snapshot identifiers and the current task version. A stale modal must fail with 409, not silently accept a newer artifact. Candidate artifacts and decision receipts cannot be edited or deleted. A new material revision needs another candidate; artifact editing is not part of this slice.

Accept closes Task/Run/Operation as succeeded and stores `accepted_decision_id`. Reject closes them as failed. Request changes closes the old Run/Operation as failed and blocks the Task with `candidate_changes_requested`; it does not dispatch another model call. Receipts include current principal, before/after task versions, artifact tuple, method and time. `authorized_user_decision` means an authorized principal submitted the command; it does not prove a human was present or independently fact-checked the output. The deterministic `fixture:echo` has a separate exact echo check and succeeds automatically.

Members can review/retry their own tasks; administrators/owners can do so for other owners according to the generated permissions. Target ownership and current authority are checked before cached mutation replay. Authority is checked again after lock waits and before commit. Browser mutations also require the established session/CSRF boundary. No review command settles a reserve, removes a hold, adjusts a counter or changes the original provenance. Review remains possible when a late financial hold exists.

## Explicit new attempt

`POST /tasks/{id}/retry` returns a Task and requires Idempotency-Key, positive `expected_version`, nonblank `reason` (4096 UTF-8 bytes maximum) and `acknowledge_new_cost: true`. Optional feedback is at most 8192 UTF-8 bytes and must be nonblank following request_changes. Only a blocked root Task in the server's retry reason allowlist can start a new attempt. A managed child, terminal task, exhausted lifetime, expired tree, revoked authority, exhausted budget or financial hold cannot use this command to bypass admission.

A new Run and Operation receive new identifiers. The old sent/unknown Action is never sent again. Existing reservations, unknown liabilities, settled costs, receipts and immutable agent/model/price pins remain. The new input contains the original goal, feedback and exact prior candidate content as untrusted source material, with matching artifact identifiers and digests. The server rebuilds this input from stored state before validating dispatch intent; a worker cannot substitute its own feedback or goal.

Each root tree has immutable maximum depth and deadline, a monotonic task counter (maximum 128) and attempt counter (maximum 384). Root max_runs is 1–10; dependency tasks have one run each and a root retry creates new dependencies. Expired admission is checked with database wall-clock time after profile lock waits; the run-insert guard also prevents spending an attempt slot after the deadline. Limits and counters do not reset on retry. A bounded input that cannot fit is rejected explicitly, never silently summarized to fit.

Cancellation fences all nonterminal descendant operations, including leased ones, and closes scheduling. It preserves liabilities. A stale worker cannot publish a candidate after cancellation. Trusted cost reconciliation remains independent of the execution lease; a deterministic fixture reservation has its separate synthetic reconciler. Cancellation is not proof that a remote call had no effect or no cost.

## Closed team execution

An agent can contain a `TeamDefinition`: `sequence`, `parallel` or `delegate_verify`, with published `agent_id`/`agent_version` members, optional per-member task (at most 4096 UTF-8 bytes), join policy and limits. Publishing validates the complete dependency plan. Task admission compiles and pins the whole nested tree before accepting it; a root retry clones those pins. A retired model does not silently change to a newly installed version.

All dependency Task rows are materialized atomically and count toward organization queue capacity up front. They wait without a Run/Operation until their dependencies are ready. The coordinator performs bounded database transitions without a network call inside a transaction. Parallel limits count direct active branches; a nested coordinator occupies one branch slot. The worker pool separately bounds leaf execution. There is no general DAG, autonomous topology rewrite or guaranteed fair scheduler in this slice.

Sequence and delegate_verify pass the previous saved candidate's exact content as untrusted context. A verifier agent's response is another candidate, not automatic factual proof. A join creates a bounded immutable manifest containing exact member candidate/artifact tuples and content. A partial join labels omissions after affected branches have closed. An oversized join fails explicitly. The aggregate still requires an authorized decision.

An individual child may be reviewed or cancelled before its candidate has been selected by the coordinator. Once selected, it is immutable for consumption and the public command returns conflict; decide or cancel through the parent/root. Managed children cannot retry themselves. An aggregate decision follows only the frozen selected-candidate closure. Pending selected child candidates receive immutable `inherited_authorized_user_decision` receipts referencing the parent decision; existing individual decisions and deterministic fixture outcomes remain intact. Earlier attempts and omitted branches never gain invented acceptance receipts.

Structural writers serialize through a permanent tree-control row with `FOR NO KEY UPDATE`, then lock existing operations, organization and depth-ordered tasks. This mode permits deferred FK `KEY SHARE` checks by a leaf committing under the tree. Leaf accounting never takes the structural gate. See `docs/TEAM-COORDINATION.md` for implementation, tests and limitations.

## Practical limits

This bounded collaboration slice does not supply shared document editing, arbitrary tool execution, full approval workflows, autonomous truth checking, complete loop remediation, MCP, sandbox isolation, corporate identity lifecycle, provider operations or performance certification. The only automatic success verifier remains the explicitly synthetic exact echo. Named paid-provider interoperability and final invoices require separate acceptance evidence.
