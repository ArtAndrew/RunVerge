# Настройка моделей и MCP

Версия0.12 проверена локально; основной сохранённый профиль работает с0.12.0
и SQL020. CORE-0.12.md (internal historical reference omitted) содержит доказательства и пределы
проверки. Полный контракт: [CONFIGURATION.md](../contracts/CONFIGURATION.md).
Страница «Настройка» и команды SDK/CLI используют одни серверные проверки.
Обычному клиенту доступ к PostgreSQL не нужен. Это ограниченный локальный выпуск,
не подтверждение готовности облачного продукта к промышленной эксплуатации.

## Порядок работы

Перед изменениями можно выполнить [продуктовую диагностику](DOCTOR.md):
`platform doctor --url https://platform.example --credentials /private/platform.json --json`.
Она читает текущую доступную конфигурацию без внешних probes и предлагает
исправления по кодам; `platform doctor --catalog --json` выдаёт каталог без сети.

1. Оператор установки регистрирует разрешённое назначение и назначение ключа.
2. Владелец организации при необходимости выдаёт человеку или сервисному агенту
   ограниченное разрешение на конкретные назначения и действия.
3. Пользователь или агент создаёт план с явными версиями подключений. План
   показывает, какие версии будут отключены и какие задачи могут остановиться.
4. Отдельная команда проверяет план без сетевого запроса к модели/MCP.
5. Если политика назначения требует одобрения, владелец одобряет точный план
   и результат проверки. Сервисный агент не может одобрить его вместо владельца.
6. Отдельная команда применяет настройки. Подключение помечается как сохранённое,
   но ещё не проверенное.
7. По отдельному действию выполняется одна проверка подключения с явным пределом
   расходов. Её результат и финансовое состояние показываются раздельно.

План нельзя изменить после создания. При конфликте версии нужно прочитать
текущее состояние и осознанно составить новый план. Сбой ответа не является
основанием автоматически создавать новое действие или заменять его ключ.

## Подготовка оператором установки

Доверенные профили задают адрес, допустимую сеть, CA, модель, тарифные допущения,
лимиты и имя секрета в окружении worker. Сам ключ в профиль не записывается.
Публичный API не позволяет агенту заменить эти поля или выбрать произвольный
адрес. Внешнее хранилище секретов может передать значение в окружение процесса;
эта версия не реализует универсальный Vault/KMS-коннектор.

`CredentialPurposeProfile` закрепляет `organization_id`, `id`, `version`, `kind`,
`endpoint_digest`, `credential_environment`, `active`. `endpoint_digest` —
SHA-256 точной UTF-8 строки адреса назначения. Ссылки на секрет начинаются с
`PLATFORM_MODEL_KEY_` или `PLATFORM_MCP_KEY_` в зависимости от вида подключения.

`ConfigurationDestinationProfile` содержит безопасный `destination` и ровно
один закрытый шаблон `model` или `mcp`. Назначение закрепляет постоянный
`target_id`, точные ID/версию назначения ключа, требование одобрения и предел
проверки. В шаблоне модели `credential_environment` оставляют пустым: при
применении сервер подставляет только заранее согласованную ссылку. Полные
JSON-примеры обоих видов, правила чисел и порядок установки приведены в
[операторской инструкции](CONFIGURATION-PROFILES.md). Описание HTTP-адаптера
модели находится в model-gateway.md.

MCP-шаблон содержит `endpoint`, `timeout_seconds`1..30,
`allow_private_network` и при необходимости `trusted_ca_pem`. Этот профиль
принимает HTTPS. Для проверки discovery оператор должен явно поставить
`discovery_unmetered_approved=true` и нулевой предел расходов; платное discovery
этим профилем не поддерживается. Зарегистрированное подключение не устанавливает
исполняемые инструменты и не разрешает `tools/call`.

Профили передают через закрытые JSON-файлы с правами0600. В примерах ниже
`platform` обозначает собранный `bin/platform` из корня репозитория:

```sh
platform install-credential-purpose --file /private/purpose.json
platform install-configuration-destination --file /private/destination.json
```

Эти две команды требуют доступа оператора к базе. Остальные `platform config`
обращаются к HTTP API с обычной учётной записью. Новые версии профилей идут
последовательно. Повторная установка прежней версии не включает её заново.
Замена активного назначения/назначения ключа отключает доверие к старой версии;
новые задачи и отправки по скопированным старым профилям будут отклонены.

## CLI без доступа к базе

Укажите `--url` либо `PLATFORM_URL`. Учётные данные передают через закрытый файл,
созданный bootstrap/командой выдачи токена, либо через `PLATFORM_TOKEN` и
`PLATFORM_ORGANIZATION_ID`. Токен не передают аргументом командной строки.
Для удалённого сервера используется HTTPS; HTTP разрешён только для явно
заданного loopback IP локального профиля.

```sh
platform config catalog --url https://platform.example --credentials /private/platform.json --json
platform config destinations list --url https://platform.example --credentials /private/platform.json --json
platform config resources list --url https://platform.example --credentials /private/platform.json --json
```

Все команды `platform config` поддерживают `--json`. Списки возвращают одну страницу и
`next_cursor`; следующую читают с `--cursor`. Команды записи дополнительно
требуют закрытый `--file` с точным JSON и явный `--key`.

| Объект | Команды после `platform config` |
|---|---|
| Возможности | `catalog` |
| Назначения и версии ресурсов | `destinations list`, `resources list` |
| Разрешения | `grants list/get/create/revoke` |
| Планы | `plans list/get/create/validate/approve/apply/verify` |
| Результаты проверки | `verifications list/get` |
| Журнал | `audit list` |

Для точного объекта нужен `--id`. Список проверок поддерживает `--plan-id`.
Точные имена JSON-полей и методы SDK приведены в контракте. Версии конфигурации
и деньги — десятичные строки: их нельзя сначала преобразовывать в JavaScript
`Number`. Пример тела создания плана:

```json
{
  "grant_id": "grant_from_current_catalog",
  "base_revision": "12",
  "ttl_seconds": 600,
  "operations": [{
    "id": "primary_model",
    "destination_id": "approved_destination",
    "destination_version": 1,
    "expected_resource_version": 0,
    "active": true
  }],
  "reason": "Подключить заранее согласованную модель"
}
```

ID и версии берут из текущих ответов. Ноль означает подтверждённое отсутствие
ресурса. Каталог `resources` этой версии перечисляет ресурсы, созданные через
новый контур настройки; старые подключения оператора остаются в обычном списке
моделей. Для такого старого слота версию указывают явно, не выводят отсутствие
из пустого нового списка. Для неактивных исторических версий сведения пока
уточняет оператор установки. Это остаётся ограничением полноты каталога.

Срок жизни плана ограничен запрошенным TTL и всеми родительскими разрешениями.
Точный срок возвращается в `expires_at` и входит в digest. Счётчики планов,
проверок и выделенного денежного предела общие у всей цепочки делегирования.
Создание дочернего разрешения или отзыв не сбрасывают накопленное использование.

## Проверка подключения и расходы

`plans verify` требует точные версию/digest применённого плана, ID операции,
`max_charge_microusd`, `acknowledge_cost=true` и причину. Для модели согласованный
предел должен покрывать закреплённый резерв и укладываться в предел назначения
и всех разрешений. Сервер создаёт обычную задачу без инструментов и с одной
попыткой; резерв записывается перед отправкой. Из ответа сохраняются безопасные
структурные сведения и digest. Текст и идентификатор ответа поставщика могут
содержать ключ, поэтому они отбрасываются.

`response_received` подтверждает получение структурно допустимого ответа.
Модельный кандидат остаётся непроверенным, задача ожидает отдельного решения.
Оценка usage не является счётом: неопределённое обязательство остаётся в учёте
и после успешной проверки связи. Итоговый счёт принимает отдельный доверенный
механизм сверки; согласие пользователя не является финансовым фактом.

MCP-проверка выполняет только negotiation/discovery и чтение списка инструментов:
до16 страниц,128 инструментов,4MiB суммарного каталога. Она сохраняет версию
протокола, количество и digest. Тексты и схемы peer не становятся инструкциями
для агента. Полный профиль, сеть, назначение ключа и версия ресурса закреплены в
lease и коротком допуске отправки; подмена другим одобренным профилем отклоняется.

Одна операция плана имеет не более одной проверки независимо от нового ключа
запроса. После подтверждённой отправки `unknown` не возвращается в очередь.
Первоначальный поздний ответ можно записать даже после отзыва доступа; это не
даёт права на новую отправку. Исходный ключ можно явно повторить для получения
его сохранённой квитанции, затем прочитать текущее состояние через GET.

## MCP-интерфейс платформы

Новый контур добавляет17 инструментов `platform_configuration_*` через тот же
HTTP API:10 читающих и7 команд записи. Все команды записи требуют отдельного
включения оператором транспорта; наличие tool в discovery не расширяет права
учётной записи. Список включает catalog, destinations/resources/grants/plans/
verifications/audit и точные create/revoke/validate/approve/apply/verify.

Всего в частном адаптере50 читающих инструментов и30 доступных для явного
включения команд записи. Профиль транспорта и его ограничения описаны в
[MCP-ADAPTER.md](MCP-ADAPTER.md); этот выпуск не добавляет полноценный MCP OAuth
resource-server или изоляцию произвольных исполняемых расширений.

## Что проверено локально

Планы, делегирование, применение и отдельные проверки подключения выполнены
на изолированных PostgreSQL-схемах с синтетической моделью и настоящим локальным
TLS MCP peer. Отчёт клиентов (internal historical reference omitted)
связывает SDK, CLI и браузерные сценарии. Это не проверка платного поставщика.

Сохранённый основной профиль отдельно прошёл обновление018→020 (internal historical reference omitted),
развёртывание (internal historical reference omitted) и
чтение через SDK/CLI/MCP (internal historical reference omitted).
После обновления новые конфигурационные коллекции были пусты, каждая организация
получила revision1; проверка не создавала задач и не запускала model/tool requests.
Исторические записи и неизвестные финансовые обязательства сохранены.
