# Диагностика настройки

`platform doctor` читает доступные текущей учётной записи настройки моделей и
MCP и выдаёт JSON-отчёт с кодами проблем и следующими действиями. Команда работает
через обычный HTTP API версии0.13.0 и не требует доступа к PostgreSQL. Версия
собственного формата отчёта — `report_version: "1"`.

```sh
bin/platform doctor --url http://127.0.0.1:8080 --credentials .local/bootstrap.json --json
bin/platform doctor --url https://platform.example --credentials /private/platform.json --plan-id PLAN_ID --json
bin/platform doctor --catalog --json
```

Можно использовать `PLATFORM_URL`, `PLATFORM_TOKEN`, `PLATFORM_ORGANIZATION_ID`.
Токены не передаются аргументом командной строки. Файл учётных данных должен быть
приватным, как у `platform config`. HTTP разрешён только для явно заданного
loopback IP; для удалённого сервера нужен HTTPS. Перенаправления не выполняются.
Весь запуск использует одну прочитанную учётную запись; сервер заново проверяет
её права при каждом чтении.

Диагностика не вызывает модели, MCP-серверы, `tools/call`, статическую validation,
apply или verify; не выдаёт разрешения, не меняет настройки и финансовые записи.
Не читает секреты worker и не печатает адреса поставщиков, их имена или ответы.
Доступность API не доказывает доступность самого поставщика.

## Как читать результат

| Поле | Значение |
|---|---|
| `assessment` | `configuration_observation`: наблюдение конфигурации, не разрешение выполнить команду |
| `inspection_complete` | Все запрошенные чтения закончились в пределах ограничений, версии каталога и выбранного плана не изменились между контрольными чтениями |
| `status: observed` | Наблюдение завершено без обнаруженных замечаний; это не health сертификат или готовность выпуска |
| `status: attention_required` | Наблюдение завершено, есть проблема или неподтверждённая проверка подключения |
| `status: incomplete` | Часть чтений не выполнена, недоступна, неоднозначна или превысила срок/объём |
| `findings[].remediation` | ID конкретного исправления из `doctor --catalog` |
| `read_only`, `external_probes` | `true` и `0`: никаких исправлений и внешних проверок в этом запуске |

Код выхода0 соответствует `observed`. Код1 — отчёт требует внимания либо команда
не выполнена. При корректных аргументах ошибки чтения/авторизации также дают
структурированный отчёт в stdout; stderr содержит только общее сообщение.
Ошибка аргументов может не создавать отчёт. Пустые списки не означают отсутствие
старых подключений или объектов, скрытых от текущего пользователя.

Данные читаются последовательно; это не атомарный снимок и не блокировка
конфигурации. Повторное чтение каталога и выбранного плана обнаруживает изменения
их версий/доступных команд. Область видимости или предки разрешения могут
измениться даже при равенстве этих полей каталога; изменения проверок или прав
после последнего запроса тоже не замораживаются. Перед любым действием нужна
текущая серверная авторизация.

По умолчанию срок всего запуска30секунд; `--timeout-seconds` принимает1..120.
Каждый список ограничен5страницами по100записей. Повтор курсора/объекта между
страницами и ненулевой курсор после пятой страницы делают отчёт неполным.
`--plan-id` ограничивает историю проверок конкретным доступным планом; список
назначений и подключений остаётся в пределах доступной области пользователя.
Верификация связывается с точными operation/scope/resource version плана.

## Безопасный порядок исправления

`--catalog` доступен без сети, токена или базы. Он содержит роли, условия,
шаблоны команд и классификацию внешних обращений. Шаблоны не исполняются и не
дают разрешений. Для `platform config` в них предполагаются текущие переменные
окружения; можно явно передать `--url` и `--credentials`.

1. При отказе доступа обращаются к владельцу за минимальным разрешением;
   диагност не назначает себе роль или новый бюджет.
2. Оператор устанавливает доверенные профили по [CONFIGURATION.md](CONFIGURATION.md).
3. Уполномоченный пользователь/агент читает текущие версии, создаёт план,
   выполняет static validation, получает одобрение при необходимости и применяет.
4. Проверка соединения запускается отдельно с точным лимитом и явным согласием.
   Если проверка уже существует, читают её; после `unknown` не создают замену.
5. Ответ на проверку означает только прежнее получение ответа. Окончательный
   счёт, качество ответа и доступность соединения сейчас — отдельные вопросы.

Отсутствие доступного receipt не разрешает новую проверку: она может быть скрыта
от этой учётной записи. Окончательное решение принимает сервер по текущим правам
и постоянной идентичности операции. Исторические неизвестные расходы остаются
видны как замечания даже после успешного ответа на соединение.

## Границы текущего блока

Это клиентская диагностика существующих configuration API. Пока нет отдельного
doctor HTTP/MCP endpoint или страницы диагностики в Workspace. Не завершены
полный каталог всех старых профилей, настройка внешнего IdP, sandbox, операторские
проверки ключей/worker, install/backup/restore и приёмка самостоятельной работы
нового агента. Этот блок не закрывает целиком W11 или W16.

`python3 scripts/dev.py doctor` остаётся отдельной проверкой локальных инструментов
разработчика. Для продуктового отчёта используйте собранный `bin/platform doctor`.
